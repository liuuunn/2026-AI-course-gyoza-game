# 結果檢討

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「看到什麼現象 → 代表什麼問題 → 下一次怎麼改」，讓 AI 像店長一樣檢討。

## 什麼時候用

每跑完一次 `npm run simulate`，要決定下一版策略怎麼改時。

## 試算結果裡有哪些線索

試算工具每天會印出：客人數、收入、備貨、宣傳、報廢（清潔費）、淨利、任務、星等、資金，以及「沒買到的客人」：

| 線索 | 意思 |
|---|---|
| 賣完買不到 | 有人想買，但貨不夠 |
| 嫌太貴 | 價格超過客人剩下的預算 |
| 想吃的沒上架 | 客人想吃的菜今天沒賣 |
| 因為討厭的菜不進門 | 上架了某位客人討厭的菜 |

## 對症下藥表

| 看到的現象 | 代表的問題 | 下一次怎麼改 |
|---|---|---|
| 賣完買不到很多 | 備貨太少 | 那樣菜多備一些（注意合計不能超過 80 份） |
| 報廢 15 份以上 | 推測：某些菜備貨多於實際想買的人數（賣出 ＋ 賣完後沒買到）。規則書：報廢 6 份起每份 3 元，16 份以上再加 50 元清運費 | 先看倉庫盤點逐道菜的報廢數，只減報廢多的那道，減到接近「賣出 ＋ 沒買到」；不要整份菜單一起減 |
| 嫌太貴很多 | 推測：該菜價格超過客人剩下的預算。注意客人買第一樣後預算會變少，第二順位的菜較容易被嫌貴 | 寫出哪天、哪道菜、幾人嫌貴，依 pricing-rules 心法 2 在範圍內降價，並估算單份收益的損失 |
| 想吃的沒上架很多 | 推測：上架組合沒有涵蓋客人想吃的菜（最多只能上架 4 樣） | 把賣得最少或報廢最多的一樣換成客人要的菜；換之前先確認新菜不是其他客人討厭的 |
| 因為討厭的菜不進門 | 推測：上架了某些客人討厭的菜，這些客人整個人不進門，什麼都不買，也不留評價 | 比較「這道菜的收入」與「被趕走的客人可能帶來的收入」，損失較大就把那道菜下架 |
| 星等往下掉 | 推測：滿意比例太低或不滿比例太高（規則書：不滿 ≥ 25% 就 −0.5，≥ 40% 就 −1）。不滿來自什麼都沒買到：賣完、嫌貴、沒上架；價格高於建議售價會讓買到的人只算「普通」 | 先算出當天滿意與不滿的人數和比例，找出不滿最多的原因再改；星等會影響隔天來客數，要優先處理 |
| ★ 我自己發現的現象：宣傳後增加來客，但淨利未改善 | 推測：新增客人帶來的收入，不夠付宣傳費和多備的成本；或是備貨沒跟著增加，多來的客人買不到（變成不滿，星等還可能下降） | 先核對數字：新增收入（與沒宣傳的版本比）− 宣傳費 − 新增備貨成本 − 新增清潔費。結果 ≤ 0 就改回不宣傳或改用 200 元；若多來的客人是「賣完買不到」，再搭配增加備貨重新試算 |

> 填表時把「實際觀察」和「推測」分開：現象欄只寫試算結果裡看得到的數字（哪一天、哪道菜、幾份、幾人），問題欄寫的都是推測，要等下一版試算結果才能確認。

## 步驟

1. 讀試算結果，逐天找出上表的現象
2. 每一個現象，照對症下藥表提出一個修改
3. **一次最多改 3 個地方**，這樣才知道是哪個修改有效
4. 把修改後的策略存成新的檔案（例如 `plans/v2.json`），不要覆蓋舊的，方便比較

## 回報格式

```text
這一版的結果：最終資金 …、星等 …、報廢 …
發現的問題：
1. 第 N 天：（現象）→（問題）
修改：
1. …
下一版檔名：
```

## 不准做的事

- 不准修改遊戲檔案（`src/` 底下的任何檔案、客人包）
- 只能新增或修改 `web-lab/plans/` 裡的策略檔
