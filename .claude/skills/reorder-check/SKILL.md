# 補貨檢查

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「數字一定要從盤點資料抄，不能自己編」，而且每個數字都要能驗算。

## 什麼時候用

- 跑完 `npm run simulate`，要決定下一版策略每樣菜備幾份時
- 在瀏覽器玩完一天，想看「倉庫盤點」頁的結果該怎麼調整時

## 資料從哪裡來

在 `web-lab` 資料夾執行：

```text
npm run simulate -- plans/策略檔.json --json
```

每一天的 `inventory` 欄位，是那天每樣上架的菜的盤點：

| 欄位 | 意思 | 怎麼驗算 |
|---|---|---|
| `name` | 菜名 | — |
| `stocked` | 早上備了幾份 | 策略檔裡的 `qty` |
| `sold` | 賣出幾份 | 打烊報表 |
| `waste` | 報廢幾份 | 備貨 − 賣出 |
| `missed` | 賣完之後，還有幾位客人想買卻沒買到 | 客人卡片上「賣完了」的數量 |
| `status` | `ok` 正常、`out` 缺貨、`over` 報廢過多 | 規則書「倉庫盤點」 |
| `suggest` | 明天建議備幾份 | 賣出 ＋ 沒買到 |

## 步驟

1. 執行上面的指令，讀每一天的 `inventory`
2. 先驗算：`waste` 有沒有等於 `stocked − sold`？對不上就停下來回報，**不要用錯的資料做建議**
3. 挑出 `status` 不是 `ok` 的菜
4. 建議備貨量：以 `suggest`（賣出 ＋ 沒買到）作為盤點資料支持的基準。若要因明天預期客流或其他原因調整，必須有使用者提供或模板列出的依據，列出原建議、調整算式及數字來源；沒有依據就保留 `suggest`，不要自行加減。若要判斷下一版完整備貨策略是否可執行，檢查所有餐點的總備貨份數、總備貨成本、宣傳費與可用資金，並核對規則書中的上架數、總份數及資金限制。總備貨成本以各菜備貨份數乘以可核對來源的單價後加總，列出算式；所有數字（包括單價）都必須來自使用者提供的資料或本模板已列出的資料來源。需要完整策略數量、單價、宣傳費和可用資金等資料；缺少任何必要資料時，明確寫「尚無法確認可執行性」，不得把單一道菜的建議當成已驗證的完整策略。
5. 同一道菜在資料中連續兩天都屬於缺貨（`out`）或報廢過多（`over`）時，提醒是持續現象，列出連續各天的狀態及備貨、賣出、沒買到／報廢數字。只有一天資料或日期不連續時，不推測連續趨勢。
6. 用下面的回報格式回報

## 回報格式

```text
策略檔：
驗算結果：通過 / 第 N 天的 ○○ 對不上（寫出哪個數字）
第 N 天：
  缺貨：菜名 備 … 賣 … 沒買到 … → 建議 …
  報廢過多：菜名 備 … 賣 … 報廢 … → 建議 …
完整策略可執行性（完整策略總備貨份數、總成本算式、宣傳費、可用資金及規則限制核對結果；缺少必要資料時寫「尚無法確認可執行性」）：
下一版每天建議的備貨量：
```

## 寫完檢查

- [ ] 每一個數字都能在盤點資料裡找到
- [ ] 所有原始數字均來自使用者提供的盤點資料或本模板列出的資料來源；每個計算結果都列出算式，資料不足時明確標示未能確認的項目

## 不准做的事

- 不准修改任何檔案（這個 Skill 只讀不寫，要改策略交給 result-review）
- 不准自己編數字，或用「大概」、「差不多」帶過
- 不准在缺少完整策略或資金資料時宣稱整體策略可執行，也不准把單一道菜的補貨建議當成完整策略已通過檢查
